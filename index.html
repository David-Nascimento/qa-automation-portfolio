01IA nos testes

A IA acelera. A revisão é minha.

Uso IA no dia a dia de QA em duas frentes: gerar cenários e casos de teste, e escrever e revisar código de automação. Ela propõe; o que entra na suíte passa pela minha revisão.

Uso 1

Gerar cenários e casos de teste

Transformo histórias e requisitos em cenários Gherkin com IA, e depois confiro a cobertura: casos negativos, limites e o que o modelo deixou de fora.

  • BDD GenerationX gera .feature e steps a partir de histórias em texto, com ChatGPT, Gemini ou DeepSeek, ou em modo estático sem IA.
  • QAXpert lê o código Ruby e sugere cenários BDD pela API do Gemini.

Uso 2

Escrever e revisar automação

Uso assistentes de código, como o Claude, para estruturar frameworks e revisar testes mais rápido. O código gerado passa pela minha leitura antes de entrar.

  • Karate API Framework foi escrito com o Claude como assistente, e o commit registra a coautoria.
  • No QA Playground, 3 commits têm a mesma marcação, então dá para ver no histórico o que foi feito com IA.

Como eu reviso o que a IA entrega

  1. Cobertura antes de volume. Um cenário gerado só entra se cobre um requisito que ainda não tinha teste.
  2. Ver falhar. Teste que nunca ficou vermelho não prova nada. Confiro que ele quebra quando a regra quebra.
  3. Sem dado real no prompt. Massa de teste e segredos ficam fora da conversa com o modelo.

Imagem sem texto alternativo na tela de login do ServeRest

Severidade crítica (axe) Prioridade baixa: app de terceiros

Quem usa leitor de tela chega na tela de login e encontra uma imagem que não é descrita.

Ambiente
front.serverest.dev/login, no Chrome via Selenium WebDriver.
Como foi achado
Cenário automatizado @a11y com axe-core (WCAG 2.1 A/AA), requisito REQ-A11Y-004.

Passos para reproduzir

  1. Abrir front.serverest.dev/login.
  2. Rodar a auditoria do axe-core com as regras WCAG 2.1 A e AA. No projeto: rake a11y.
  3. Conferir as violações de nível crítico ou pior.

Esperado

Nenhuma violação de nível crítico na tela de login.

Obtido

Regra image-alt: imagem sem texto alternativo. Também aparece color-contrast de nível sério, que fica abaixo do corte do cenário.

Evidência
Relatório do axe anexado ao próprio cenário, com a lista de violações.
Tratamento
Como o app não é nosso, a regra entrou no baseline com o motivo e a data documentados. O teste continua protegendo a tela contra qualquer violação nova, e a entrada sai do baseline quando o problema for corrigido.

04Teste de API

Uma jornada de compra, do cadastro à limpeza.

Um olhar guiado dentro do cenário @e2e do Karate API Framework, contra a API pública ServeRest: como as chamadas passam dados umas para as outras, o que cada asserção confere e como o cenário limpa o que criou.

1 / 9

Criar o administrador

POST/usuarios

Asserções implementadas

  • Status 201.
  • O _id devolvido fica salvo e entra na lista de limpeza.

Por que esta etapa importa

Cada execução cria o próprio usuário, com e-mail único gerado pela DataFactory. Nada depende de um cadastro feito à mão, então a suíte roda em paralelo sem conflito.

Código real criar-usuario.feature ↗

* def usuario = karate.toJson(factory.usuario(administrador))
Given url baseUrl
And path 'usuarios'
And request usuario
When method post
Then status 201
* def id = response._id

2 / 9

Autenticar o administrador

POST/login

Asserções implementadas

  • Status 200.
  • O cabeçalho authorization vira o token das próximas chamadas.

Por que esta etapa importa

O token sai do usuário que acabou de ser criado, e não de uma credencial fixa guardada no código.

Código real login.feature ↗

Given url baseUrl
And path 'login'
And request { email: '#(email)', password: '#(password)' }
When method post
Then status 200
* def token = response.authorization

3 / 9

Publicar um produto com 10 unidades

POST/produtos

Asserções implementadas

  • Status 201.
  • O produto entra na lista de limpeza junto com o token do administrador.

Por que esta etapa importa

Começar com um estoque conhecido é o que permite conferir a conta nas etapas seguintes.

Código real jornada-de-compra.feature ↗

* def produto = call read('classpath:common/produtos/criar-produto.feature')
    { token: '#(sessaoAdm.token)', quantidade: 10 }
* eval karate.appendTo('recursos', { caminho: 'produtos', id: produto.id, token: sessaoAdm.token })

4 / 9

Cliente se cadastra e entra

POST/usuarios + /login

Asserções implementadas

  • Status 201 no cadastro e 200 no login, pelos mesmos helpers.
  • Perfil sem permissão de administrador.

Por que esta etapa importa

A compra é feita por outro usuário, sem perfil de administrador, como acontece de verdade na loja.

Código real jornada-de-compra.feature ↗

* def cliente = call read('classpath:common/usuarios/criar-usuario.feature') { administrador: 'false' }
* def sessaoCliente = call read('classpath:common/auth/login.feature')
    { email: '#(cliente.usuario.email)', password: '#(cliente.usuario.password)' }

5 / 9

Reservar 3 unidades no carrinho

POST/carrinhos

Asserções implementadas

  • Status 201.
  • Registra o cancelamento do carrinho na limpeza, caso o cenário pare no meio.

Por que esta etapa importa

Se o teste falhar antes de concluir a compra, a limpeza devolve o carrinho e não deixa lixo na API.

Código real jornada-de-compra.feature ↗

Given path 'carrinhos'
And header Authorization = sessaoCliente.token
And request { produtos: [ { idProduto: '#(produto.id)', quantidade: 3 } ] }
When method post
Then status 201

6 / 9

Conferir a reserva no estoque

GET/produtos/{id}

Asserções implementadas

  • Status 200.
  • quantidade == 7.

Por que esta etapa importa

A regra de negócio importa mais que o status: 10 menos 3 tem que dar 7. Um 200 com estoque errado seria um bug passando despercebido.

Código real jornada-de-compra.feature ↗

Given path 'produtos', produto.id
When method get
Then status 200
And match response.quantidade == 7

7 / 9

Concluir a compra

DELETE/carrinhos/concluir-compra

Asserções implementadas

  • Status 200.
  • message == 'Registro excluído com sucesso'.

Por que esta etapa importa

Confere a resposta exata da API, não só o código de status.

Código real jornada-de-compra.feature ↗

Given path 'carrinhos', 'concluir-compra'
And header Authorization = sessaoCliente.token
When method delete
Then status 200
And match response.message == 'Registro excluído com sucesso'

8 / 9

O estoque não volta

GET/produtos/{id}

Asserções implementadas

  • Status 200.
  • quantidade continua 7.

Por que esta etapa importa

Concluir a compra não pode devolver as unidades ao estoque. Esta é a checagem que pegaria um bug de devolução indevida.

Código real jornada-de-compra.feature ↗

Given path 'produtos', produto.id
When method get
Then status 200
And match response.quantidade == 7

9 / 9

Limpar tudo o que foi criado

DELETEafterScenario

Asserções implementadas

  • Remove carrinho, produto e usuários, em ordem inversa à criação.
  • Sem asserção de status, de propósito.

Por que esta etapa importa

A ordem inversa respeita as dependências da API. E a limpeza é tolerante: uma falha aqui é registrada no log, mas nunca reprova o cenário nem esconde o resultado real do teste.

Código real limpar.js ↗

var recursos = karate.get('recursos') || [];
for (var i = recursos.length - 1; i >= 0; i--) {
  try {
    karate.call('classpath:common/limpeza/remover.feature', recursos[i]);
  } catch (e) {
    karate.log('Limpeza ignorada para', recursos[i].caminho, ':', e);
  }
}
Rodar o projeto localmente

  1. Clonar o repositório

    Precisa de Java 17 ou superior e Maven 3.8 ou superior. O Docker é opcional.

    git clone https://github.com/David-Nascimento/karate-api-framework.git
cd karate-api-framework

  2. Conferir os helpers

    Os testes unitários do código de apoio não precisam de rede nem da API.

    mvn test -Dtest=DataFactoryTest

  3. Rodar a suíte

    Contra a API pública, ou contra uma cópia local do ServeRest, que é mais rápida e não afeta o ambiente compartilhado.

    # API pública
mvn test -Dkarate.env=dev

# API local
docker compose up -d serverest
mvn test -Dkarate.env=local

# só esta jornada, ou só o smoke
mvn test -Pe2e
mvn test -Psmoke

  4. Sem Java instalado

    O Docker sobe a API, espera ela ficar saudável e roda a suíte num container.

    docker compose --profile testes up --build --abort-on-container-exit --exit-code-from testes

O relatório fica em target/karate-reports/karate-summary.html. Esta página explica o cenário; ela não envia requisições nem mostra uma execução gravada.
